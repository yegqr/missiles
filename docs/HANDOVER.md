## 2. Головне правило: доба нальоту

Доба рахується **з 12:00 до 12:00 за київським часом** і підписується датою
початку. Наліт 22:00 → 05:00 це одна подія; календарна північ ріже її навпіл.

Функція `raid_day(timestamptz) -> date` робить це перетворення. Уся добова
аналітика вже приведена до `raid_day` — не перераховуйте самі.

Відсічка прогнозу — **12:00 доби `d`**, тобто рівно початок вікна. Звідси
зручний наслідок: усе, що відоме до відсічки, — це рівно попередня доба
нальоту `d-1`. Ніякої арифметики годин не потрібно.

## 3. Що можна подавати в модель, а що ні

`v_daily_features` розділена навмисне:

| Префікс | Що це | Можна в модель |
|---|---|---|
| `*_prev` | стан за добу `d-1` | **так** |
| `night_*`, `holiday_*`, `dow`, `month`, `night_hours` | календар і прогноз погоди | **так** |
| `y_*` | те, що сталося всередині вікна | **ні, це ціль** |
| `mig31k_same_window` | сигнал усередині вікна | **ні** |

**Найпідступніша пастка — погода.** Прогноз погоди на ніч є валідною ознакою,
бо о 12:00 він уже виданий. Фактична погода тієї ночі — витік. У базі це
розведено: `weather_hourly` — факт, `weather_forecast` — прогноз із власним
`issued_at`. У `v_daily_features` зараз підтягнуті **фактичні** нічні агрегати
(`night_cloud_low_avg` тощо) — для чесного бектесту їх треба замінити на
прогнозні зрізи з `weather_forecast`, де `issued_at < 12:00` доби `d`.
Це відомий борг, він позначений тут навмисно.

## 4. Що виміряно на даних

Перевірено на 973–1188 добах 2024–2026. Базова частка «атака була» — 61–69%,
тобто наївна модель «завжди так» дає цю точність. Це планка.

**Працює:**

| Ознака | Ефект |
|---|---|
| інтенсивність напередодні | 51% → 85% атак (розкид 34 пункти) — найсильніше |
| вітер уночі | тихо <8 км/год → 75%, сильний >15 → 57% |
| тривалість ночі | довга >12 год → 64%, коротка <9 год → 55% |

**Не працює** (перевірено, не витрачайте час):

- фаза місяця — 69% проти 70%, різниці нема
- хмарність — немонотонно, 62–71%
- зльоти МіГ-31К напередодні — 61% проти 61%
- українські й російські свята — вибірки по 6–24 доби, шум

**Окремо:** МіГ-31К усередині того самого вікна дає втричі більше ракетних
треків (0.39 → 1.16) і вдвічі більше хвилин тривог. Тобто сигнал реальний,
але живе години, а не добу. Для горизонту «сьогодні вночі» він марний;
для контуру «удар найближчі 1–2 години» — сильний.

## 5. Обмеження даних, які змінюють постановку

**Кількостей засобів по Києву не існує.** Повітряні Сили публікують лише
національні числа за ніч. Тому:

- `y_drone_tracks` / `y_missile_tracks` — це **кількість спостережень**
  (повідомлень супроводу цілей курсом на Київ), а не кількість бортів
- `drones_launched_ua` — точне число, але по всій країні
- складати їх між собою не можна

**Два режими доступності.** Формат супроводу цілей став щільним лише з 2024.
За 2023 рік у каналі ПС всього 5 добових зведень на 298 діб.

| Період | Розмітка |
|---|---|
| 2022-02 → 2023-12 | тільки тривоги; треків і зведень майже немає |
| 2024-01 → зараз | повна: 980 діб |

Практичний висновок: навчальна вибірка — **2024–2026**. Ранній період
придатний лише для ознак на основі тривог.

**Зміна режиму у вересні 2026.** З 05.09.2026 середні хвилини тривог у Києві
впали з 553 до 179, 06.09 не було жодної тривоги. Це збігається з переговорами
про припинення ударів по містах. Якщо режим триває, модель, навчена на
попередніх даних, систематично перебільшуватиме. Ознаки під це немає.

## 7. Схема бази

**Сирі дані** (не змінювати вручну):
`tg_messages` — усі зібрані повідомлення; `alerts` — тривоги з усіх джерел;
`weather_hourly`, `weather_forecast`; `readiness_signals`; `calendar_days`.

**Спостереження:** `attack_observations` — одне твердження одного джерела про
одну добу, з посиланням на повідомлення (`evidence_msg_id`). Джерела не
перезаписують одне одного: розбіжність — це дані.

**Похідні представлення:**

| Представлення | Що дає |
|---|---|
| `v_alerts_canonical` | один безрозривний ряд тривог на регіон |
| `v_canon_daily` | добові агрегати тривог |
| `v_weather_daily` | добова погода, з окремим нічним вікном 22:00–06:00 |
| `v_daily_labels` | лейбли з позначкою впевненості й суперечності |
| `v_daily_features` | **головна таблиця для навчання** |
| `v_health` | стан конвеєра |

Пріоритет джерел — таблиця `alert_sources`. Джерело нижчого пріоритету бере
слово лише там, куди не дотягується вище. Наш парсер витісняє чужий датасет
автоматично.

## 8. Що робить система сама

| Скрипт | Частота | Що |
|---|---|---|
| `alerts.sh` | 5 хв | тривоги по місту з реєстру КМДА |
| `telegram.sh` | 15 хв | добір повідомлень + перерозбір |
| `weather.sh` | година | оперативна погода + прогноз |
| `daily.sh` | доба, 06:40 | реаналіз ERA5 + продовження календаря |
| `health.sh` | доба, 09:00 | звіт про стан |

Усе в cron користувача `ye`. Кожен скрипт бере `flock`; кроки ізольовані —
збій погоди не зупиняє тривоги.

Парсери роблять **повний перерозбір** (видаляють свої попередні рядки і пишуть
заново), але мовчки пропускаються, якщо канал не виріс. Тому правила розбору
можна міняти й перезапускати без побічних ефектів.

**Перевірка живості:** `./scripts/health.sh`. Ненульовий код виходу означає,
що якийсь потік мовчить довше дозволеного (`ingest_expectations`). Стан
`пропущено` — це крок, що свідомо нічого не зробив, а не поломка.

## 9. Відомі борги

1. У `v_daily_features` нічна погода береться фактична. Для чесного бектесту
   потрібні прогнозні зрізи з `weather_forecast` за `issued_at < 12:00`.
   Дані для цього накопичуються з 07.09.2026.
2. `visibility` в історії порожня: ERA5 цієї змінної не має. Накопичується
   вперед із forecast-API.
3. Наслідки по місту (влучання, загиблі, поранені) не збираються —
   таблиці `attack_events` і `losses_daily` порожні.
4. Пороги порядкової шкали тяжкості 0–3 ще не відкалібровані:
   чекає визначення межі «масованої атаки» від замовника.
5. Ознаки під переговорний режим (див. §5) немає.
